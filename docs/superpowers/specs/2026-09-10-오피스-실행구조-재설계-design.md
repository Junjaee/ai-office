## 한 장 요약 (비개발자용)

- **바뀌는 것**: "시작" 버튼이 실제 자동화를 돌린다. 전체를 한 번에 돌리는 **[전체 시작]**과 자동화 하나씩 돌리는 **[시작]**이 모두 있다. 화면에는 직원(=담당 업무)이 **쉬는 중 · 일하는 중 · 끝남 · 오류** 중 무엇인지만 보인다. 회의실·대표실·대표 승인·브리핑·보고 발행 같은 연출은 전부 없앤다. **직원은 쉴 때 라운지 소파에 있고, 일할 때 자기 책상으로 걸어가 앉는다** — 이동은 상태가 바뀔 때만 있고 랜덤 행동·말풍선은 없다.
- **전제(가장 중요)**: 자동화는 GitHub Actions(`workflow_dispatch`)로 실행되지만, 실제로 돌리는 **실행기(runner)**는 국내 IP여야 한다(국회 사이트가 해외 IP를 막아 GitHub이 제공하는 해외 서버로는 수집이 안 됨). 실행기를 **사무실 PC**에 둘지 **국내 IP 서버**(예: Oracle Cloud 무료 티어 서울·춘천 리전)에 둘지는 **아직 미정**이며, 워크플로의 `runs-on` 라벨 하나만 바꾸면 어느 쪽으로든 옮길 수 있게 구현한다. 어느 쪽이든 **실행기가 꺼져 있으면 버튼을 눌러도 아무것도 실행되지 않고, 매일 09:00 예약 실행도 밀린다** → 11절 질문 1(미정, 둘 다 지원).
- **화면 배치가 바뀐다**: 지금은 부서 방 12개를 4열 3행으로 항상 그린다. 바뀐 뒤에는 **자동화가 연결된 부서만** 그리고, 행 수는 보이는 방 수에 맞춘다(4열은 유지, 부서 12개 id는 그대로). 국회 사무실은 당분간 "회의록 수집" 방 하나만 보인다 → 11절 질문 3.
- **기다리는 시간**(실행기가 켜져 있을 때): 누르면 바로 "시작 요청됨", 30초 안에 "일하는 중", 약 3분 뒤 "끝남". 예비 경로(사이트 재배포)는 3~10분.
- **실행기가 며칠 꺼져 있으면**: 노란 배너 "예약 실행이 밀리고 있어요 · 실행기가 켜져 있는지 확인해 주세요"가 뜬다. 조용히 "쉬는 중"으로만 보이지 않는다 → 11절 질문 7.
- **보호**: 실행 버튼에 로그인·PIN 같은 보호를 두지 **않는다**(사용자 결정). 사이트 주소 비공개 유지, Worker의 중복 실행 방지, 사무실당 하루 실행 상한(50회)으로만 막는다 → 11절 질문 2(보호 없음).
- **결정할 것**: 11절 질문 7개(질문 1·2·3·4는 답변이 기록되어 있음).

## 1. 목표와 결정할 것

### 1.1 한 줄 목표

**"시작" 버튼을 누르면 실제 자동화가 돌고, 화면에는 직원(=담당 업무)이 지금 쉬는 중인지 · 일하는 중인지 · 끝났는지 · 오류인지만 보인다.** 그 외의 연출(회의실·대표실·대표 승인·비서 브리핑·보고 발행·결과물 창고·지시창)은 전부 없앤다. 라운지는 "쉬는 곳"으로만 남기며, 직원 이동은 상태가 바뀔 때(쉬는 중↔책상)만 일어난다.

### 2.2 버튼 두 개

| 버튼 | 위치 | 하는 일 | 눌렀을 때 화면 |
|---|---|---|---|
| **▶ 전체 시작** | 헤더 우측 | 이 사무실의 연결된 자동화 중 **아직 일하지 않는 것**을 순서대로 시작 요청 | 토스트 "회의록 수집 시작 요청했어요" / 여러 개면 "2개 시작 요청, 1개는 이미 실행 중" |
| **▶ 시작** | 자동화 카드마다 | 그 자동화 하나만 시작 요청 | 토스트 "{이름} 시작 요청했어요" |

버튼 상태 규칙
- 카드의 **[시작]**: 누르는 순간 비활성("요청 중…"). 응답이 `accepted`면 그대로 **일하는 중 · "시작 요청됨"**이 되어 계속 비활성(끝남·오류·쉬는 중이 될 때까지). 응답이 `skipped`(다른 탭·다른 사람·예약 실행이 이미 돌리고 있음)면 토스트 "이미 실행 중이에요"(또는 "방금 요청했어요")를 띄우고 버튼은 다음 상태 확인(≤10초) 때 화면 상태를 따른다.
- 헤더의 **[전체 시작]**: 연결된 자동화가 **모두** 일하는 중이면 비활성. 하나라도 쉬는 중·끝남·오류면 활성이고, 누르면 일하는 중이 아닌 것만 요청한다(이미 도는 것은 결과에 `skipped`로 돌아와 토스트에 "1개는 이미 실행 중"으로 합산). 누르는 순간 비활성("요청 중…") → 응답 뒤 규칙대로.
- 따라서 **같은 탭에서 같은 버튼을 연타하는 것은 불가능**하다(첫 클릭에 비활성). "이미 실행 중이에요" 토스트는 다른 탭·다른 사람·예약 실행과 겹쳤을 때, "방금 요청했어요"는 Worker의 60초 간격 보조 규칙에 걸렸을 때만 보인다.
- 준비 중(워크플로 없음) 자동화는 카드에 버튼이 없다.
- 실행 연결이 안 됐으면(토큰 미설정·만료) 버튼 대신 "실행 연결이 안 돼 있어요 — 설정 안내 보기".

사용자가 체감하는 순서(실행기가 켜져 있을 때)
1. 클릭 → 즉시 카드가 **일하는 중 · "시작 요청됨"**, 직원이 라운지 소파에서 일어나 자기 책상으로 걸어가 앉아 타이핑 자세로 바뀜.
2. 5~30초 → 부제 "시작한 지 1분째"로 바뀜(GitHub이 실제로 실행 시작).
3. 약 2분 → 실행 종료.
4. 약 30초 → **끝남 · "신규 3건, 확정본 교체 1건"**. 직원마다 끝남 배지.

실행기가 꺼져 있으면(사무실 PC든 서버든 같다): 1번 뒤 90초가 지나도 시작이 안 되면 부제가 **"실행기 기다리는 중"**이 되고 위쪽에 노란 배너가 뜬다. 실행기가 켜지면 자동으로 이어진다(별도 조작 없음). **단, 24시간 안에 실행기가 켜지지 않으면 GitHub이 그 대기 요청을 취소한다.** 그 뒤에는 예약이 있는 자동화는 "예약 실행이 밀리고 있어요" 배너(D11)로, 수동 전용 자동화는 마지막 결과 그대로("끝남"·"마지막 실행 N일 전") 보이므로 실행기를 켠 뒤 다시 [시작]을 눌러야 한다.

### 2.3 픽셀 사무실 (OfficeWorld)

원칙: **이동은 상태 변화 때만. 말풍선·랜덤 행동 없음.** 상태는 위치·자세·배지·방 색으로만 보인다.

| 상태 | 위치·모습 | 이름표 배지 | 방(부서) |
|---|---|---|---|
| 쉬는 중 | 라운지 소파에 앉아 있음(a-sit) | 회색 점 | 흰색 |
| 일하는 중 | 라운지(또는 현재 위치)에서 자기 책상으로 걸어가 앉아 타이핑(a-type). 진행바 없음(실제 진행률이 없으므로) | 파란 점(깜빡) | 하늘색 + 테두리 펄스, 카메라가 이 방을 따라감 |
| 끝남 | 책상에 앉은 채(a-sit) | 초록 ✓ (그날 계속; 자정 또는 다음 실행 전까지) | 초록 |
| 오류 | 책상 옆에 서서(a-idle) | 빨간 ! | 빨강 |
| 준비 중 (설정으로 켠 경우만) | 책상, 반투명 | "준비 중" | 점선 회색 |

- **페이지를 처음 열 때는 걷기 없이** 각자 상태에 맞는 위치(쉬는 중=라운지 좌석, 그 외=책상)에 바로 놓는다. 이동은 그 뒤 **상태가 바뀔 때만** 일어난다: 쉬는 중→일하는 중은 라운지→책상, 끝남·오류→쉬는 중으로 돌아갈 때(다음 날 36시간 규칙 등)는 책상→라운지. 그 밖의 전이(일하는 중→끝남/오류, 끝남↔오류)는 제자리에서 자세·배지만 바뀐다.
- 라운지 좌석이 부족하면 라운지 안에 서서 대기(a-idle, 회색 점). 라운지 위치·좌석 좌표는 `world.ts`의 `LOUNGE_ROOM`을 재사용한다. **배치 규칙: 보이는 부서 방이 늘어나 행이 늘어도 라운지는 항상 마지막 행 아래(또는 오른쪽)에 고정**된다.
- 방 머리: 아이콘 + 부서 이름 + 상태 점 + "일하는 중 2"처럼 직원 수.
- 회의실·대표실(CEO 캐릭터 포함)은 없다. 라운지는 "쉬는 곳"으로만 남는다(회의·커피·잡담 없음). 실행기 상태는 그림 안에 그리지 않고 **배너 한 곳**에서만 보여준다.
- 숨긴 방은 그리지 않는다. 보이는 방을 왼쪽 위부터 4열로 채우고 **행 수는 방 수에 맞춘다**(국회: 1방 → 1행, 홈: 0방 → 빈 상태 문구). 지금의 4열 3행 고정 배치는 없어진다(D7).
- 전체 보기(fit) 줌에서도 직원 이름(=업무명)은 작은 글씨로 계속 보인다(지금은 숨겨짐).
- 직원을 클릭하면 아래 카드의 그 줄이 강조되며 스크롤된다(프로필 모달 없음).
- 좌석은 방마다 6석(2줄×3). 자동화 하위 작업이 부서당 6개를 넘지 않도록 테스트로 강제. 라운지 좌석 수는 `LOUNGE_ROOM`의 소파 좌석 좌표 수이며, 넘치면 위 규칙대로 서서 대기.

상태 이름
- 쉬는 중 / 일하는 중 / 끝남 / 오류 / 준비 중

부제(그 외)

배너
- 🔴 "{자동화 이름}이(가) 실패했어요 · 자세한 기록 보기"
- 🟡 "실행기가 꺼져 있는 것 같아요 · 켜지면 자동으로 시작돼요" (대기 90초 초과)

- 성공: "{이름} 시작 요청했어요" / 전체: "2개 시작 요청, 1개는 이미 실행 중"

## 3. 직원 상태 모델 (구현 상세 — 개발용)

> 비개발자용 요약: 이 절은 "화면의 쉬는 중·일하는 중·끝남·오류를 무엇을 보고 정하는가"를 코드 수준으로 적은 것이다. 요지는 세 가지. (1) GitHub이 "지금 돌고 있다"고 하면 **일하는 중**, (2) 결과 파일이 이번 실행 것이면 **끝남**(파일이 실패라고 하면 **오류**), (3) 36시간 넘게 실행이 없으면 **쉬는 중**(예약이 있는데도 없으면 노란 배너). 직원(업무)은 자기 자동화가 도는 동안 전원 일하는 중이고, 끝난 뒤에는 결과 파일에 적힌 업무별 결과를 따른다.

### 3.1 두 층위

| 층위 | 화면 요소 | 단위 |
|---|---|---|
| 자동화 (= 팀 = 부서 카드, 시작 버튼 단위) | 카드 pill, 방 색 | `public/status/<ws>/<id>.json` 한 파일, 워크플로 한 개 |
| 하위 작업 (= 직원, 이름은 업무명) | 픽셀 직원, 카드 안 목록 | 설정 `automations[].tasks[]` 항목 |

### 3.2 타입 (`app/status-rules.ts`, 순수 함수, `import type`만 허용)

```ts
export type TaskState = "idle" | "running" | "done" | "error" | "planned";
export type RunPhase  = "planned" | "idle" | "requested" | "queued" | "running" | "finishing" | "done" | "error";

export const LABELS: Record<TaskState, string> = {
  idle: "쉬는 중", running: "일하는 중", done: "끝남", error: "오류", planned: "준비 중",
};
export const STATE_CLASS: Record<TaskState, string> = {
  idle: "waiting", running: "working", done: "done", error: "error", planned: "planned",
};

export type AutomationView = {
  id: string; dept: string; name: string;
  phase: RunPhase;            // 내부 단계
  state: TaskState;           // 화면 pill (phase → 4어휘)
  sub: string;                // 부제 한 줄
  warn?: "runner_waiting" | "schedule_missed";   // 노란 배너 사유 (규칙 3·10a)
  tasks: Record<string, { state: TaskState; note: string }>;
  lastRunAt?: string; nextRun?: string; runUrl?: string; link?: string;
  counts?: Record<string, number>; log?: string[];
};
export type DeptView = { state: TaskState | "none"; runningCount: number; automationIds: string[] };
```

phase → state 매핑: `requested|queued|running|finishing → running`, 나머지는 동명.

### 3.3 자동화 판정 규칙 `deriveAutomationView(def, file, run, local, now, source)`

입력
- `def`: 사무실 설정의 자동화 정의
- `file`: 상태 파일 v2 (없으면 null)
- `run`: 그 워크플로의 **최신 유효 run** (Worker `/api/status`가 전달; `conclusion`이 `cancelled`·`skipped`인 run은 Worker가 제외하고 그 다음 run을 준다)
- `local`: 이 브라우저에서 방금 누른 요청 `{ requestId, at }` (sessionStorage, 3분 뒤 만료). **`/api/run` 응답이 `accepted`인 자동화에만 저장**된다(4.4절) — `skipped`면 저장하지 않으므로 규칙 2가 잘못 켜지지 않는다
- `source`: 상태 파일을 어디서 읽었는지 `"github"`(Contents API) | `"static"`(정적 파일)

규칙은 위에서부터 첫 번째로 맞는 것을 적용한다.

| # | 조건 | phase | 부제 |
|---|---|---|---|
| 1 | `def.workflow` 없음 | planned | "준비 중" |
| 2 | `local`이 3분 이내이고, `run`이 없거나 `run.requestId !== local.requestId` | requested | "시작 요청됨" |
| 3 | `run.status === "queued"` | queued | 90초 미만 "시작 준비 중", 90초 이상 "실행기 기다리는 중" (`warn: "runner_waiting"` → 노란 배너) |
| 4 | `run.status === "in_progress"` | running | "시작한 지 N분째" |
| 5 | `run.status === "completed"` && `conclusion ∈ {failure, timed_out, startup_failure}` | error | **`file.run_id === run.id`이면 `file.summary`(Python이 남긴 한국어 한 줄, 4.7절)**, 아니면 "실행 실패 · 자세한 기록 보기". 두 경우 모두 "자세한 기록 보기" 링크 |
| 6 | `run.status === "completed"` && `conclusion === "success"` && 파일이 이 run의 것이 아님(`file.run_id !== run.id` 이고 `file.updated_at < run.startedAt`) | 경과 < T이면 finishing "결과 정리 중", 아니면 error "결과가 올라오지 않았어요 · 자세한 기록 보기" | T = source가 github면 5분, static이면 15분 |
| 7 | `file.running === true` (**구버전 파일 호환 전용**. 새 파이프라인은 `running:true`를 쓰지 않으므로(4.7절) 마이그레이션 전 파일에만 걸린다) | `now − file.updated_at < 3 × (file.duration_sec ?? 300)`이면 running "실행 중", 아니면 error "결과를 못 받았어요" | 실행 중 실행기 종료의 실제 대응은 규칙 5(R7) |
| 8 | `file` 없음 | idle | "아직 실행한 적 없어요" |
| 9 | `!file.ok` | error | `file.summary` (한국어 한 줄) |
| 10a | `def.schedule` 있음 && `now − file.updated_at > 36시간` (`STALE_HOURS` 유지) | idle | "예약 실행이 안 되고 있어요 · 마지막 실행 N시간 전" (`warn: "schedule_missed"` → 노란 배너 "예약 실행이 밀리고 있어요 (마지막 실행 N시간 전) · 실행기가 켜져 있는지 확인해 주세요") |
| 10b | `def.schedule` 없음 && `now − file.updated_at > 36시간` | idle | "마지막 실행 N시간 전" |
| 11 | 그 외 | done | `file.summary` |

주의
- 규칙 5에서 잡이 실패해도 Python은 `report(ok=False, summary=한국어)`로 파일을 **push한 뒤** `return 1` 하므로(4.7절), Contents API 경로에서는 run 종료와 거의 동시에 `file.run_id === run.id`인 파일이 보인다. 정적 폴백에서는 3~10분 동안 "실행 실패 · 자세한 기록 보기"가 먼저 보이다가 파일이 도착하면 한국어 문구로 바뀐다.
- 규칙 6에서 "run이 오래된 것"(예: 어제 성공한 run, 파일도 어제 것)은 `file.updated_at ≥ run.startedAt`으로 같은 run이라고 본다. run_id가 없는 구버전 파일도 이 조건으로 통과한다.
- 예약(cron) 실행도 같은 규칙으로 보인다(`local`만 없음).
- **실행기가 며칠 꺼진 경우의 흐름**: 예약 run이 `queued`로 생김 → 90초 뒤 규칙 3 "실행기 기다리는 중"+배너 → 24시간 뒤 GitHub이 취소 → Worker가 cancelled를 제외해 `run`은 이전 성공 run이 됨 → 규칙 6은 같은 run(파일이 그 run 것)이라 통과 → 파일이 36시간 넘게 오래됐으므로 **규칙 10a** "예약 실행이 안 되고 있어요"+배너. 배너는 실행기가 켜져 다음 예약(또는 수동 시작)이 성공할 때까지 유지된다. 예약이 없는 수동 전용 자동화는 10b로 조용히 "쉬는 중"이 되며, 이는 정직한 표현이다(예약이 없으니 밀린 것도 없다).
- 규칙 10a는 "예약 시각을 지났는가"를 계산하지 않는다(cron 파싱 없이 36시간 기준만 씀). 매일 09:00 예약이면 어제 09:03 실행 뒤 오늘 실행이 빠지면 오늘 21:03부터 배너가 뜬다. 더 빨리 알리려면 2차에서 `def.schedule`을 cron으로 바꿔 "예정 시각 + 2시간" 기준으로 좁힐 수 있다.

### 3.4 하위 작업(직원) 판정 `deriveTaskStates(def, view, file)`

| 자동화 phase | 직원 상태 |
|---|---|
| planned | 전원 planned |
| requested / queued / running / finishing | `planned:true`가 아닌 직원 전원 running (실행 도중 작업별 세분화는 커밋 없이는 불가하므로 정직하게 "팀 전체가 일하는 중"). planned 직원은 planned |
| done / error / idle | `file.tasks[]`에서 같은 `id`의 `status`·`summary`를 그대로. 파일에 없는 직원은 자동화 상태를 상속. planned 직원은 planned |

**끝남/쉬는 중의 뜻(고정)**
- 끝남 = 이번 실행에서 그 업무가 돌았다(결과 0건이어도 끝남, note "교체 0건").
- 쉬는 중 = 이번 실행에서 돌지 않았다, 또는 36시간 넘게 실행이 없었다.
- 준비 중 = 아직 자동화가 없다(집계·시작 대상에서 제외).

### 3.5 부서·집계 규칙

- `deriveDeptView(dept)`: 그 부서에 workflow 있는 자동화가 0개 → `none`(기본 숨김, `showPlanned`면 회색). 있으면 **error > running > done > idle**의 최악값. 한 부서에 자동화 여러 개 허용(`byAutomation`으로 키 변경, 지금의 `byDept` 덮어쓰기 제거).
- 요약 4칸 = 보이는 부서의 **planned가 아닌 직원** 수를 상태별로 센다. 부제 "자동화 N개 중 M개 실행 중"(N = workflow 있는 자동화).
- 배너 집계: `warn`이 하나라도 있으면 사유별로 배너 1줄(자동화 여러 개가 같은 사유면 한 줄로 합침).
- 기존 `ops`/`secretary` 파생 상태(`status.ts` L41-42)는 삭제(요약 4칸이 대신).

### 4.1 전체 그림

```

    │  POST /api/run { ws, automation | "all", requestId }
    ▼
[Cloudflare Worker ai-office]  (GITHUB_TOKEN은 여기에만)
    │  ① 출처 확인(Origin/Host 대조)  ② 허용 목록(사무실 설정) 확인  ③ 하루 실행 상한(사무실당 50회)
    │  ④ runs API: 이미 queued/in_progress면 건너뜀  ⑤ 60초 안 재요청이면 건너뜀
    │  ⑥ POST …/actions/workflows/minutes.yml/dispatches { ref:"main", inputs:{ request_id } } → 204
    ▼
[GitHub Actions]  run 생성(queued) → self-hosted 실행기(`runs-on` 라벨 `kr-office`: 사무실 PC 또는 국내 서버) 픽업 → in_progress
    │  python collect_minutes.py … (약 2분)
    │  report_status.report(…v2 필드…) → git commit "status: minutes …" → git push
    ▼
[GitHub 저장소 main]  public/status/assembly/minutes.json 갱신
    │                                   └─▶ (웹훅) Cloudflare Workers Builds 재배포 3~10분 → 정적 파일 갱신(폴백)
    ▼
[Worker GET /api/status]  runs API + Contents API(상태 파일 직접 읽기) → 15초 메모리 캐시
    ▼
[브라우저]  10초(활성)/60초(평소) 폴링 → 3절 규칙으로 화면 갱신
```

### 4.2 `POST /api/run`

요청: `{ "ws": "assembly", "automation": "minutes" | "all", "requestId": "req-20260911090001-a1b2" }` (requestId는 브라우저가 생성: `req-` + 시각 + 4자 난수. **"all"이면 한 requestId를 이번에 dispatch되는 모든 자동화에 같이 넣는다** — 자동화마다 run은 따로 생기지만 `display_title`에 같은 requestId가 들어가므로 규칙 2 매칭에 문제없다)

처리 순서(`worker/run-api.ts`, fetch를 인자로 받는 순수 함수 + `worker/index.ts` 어댑터)

1. 메서드 POST, `Content-Type: application/json`, 본문 1KB 이하. 아니면 400/405.
2. 출처 확인: `Origin` 헤더가 **있는데** 요청 호스트와 다르면 403. `Sec-Fetch-Site`가 있고 `cross-site`면 403. 둘 다 없으면(curl) 통과 — 1단계 검증을 curl로 할 수 있게.
3. 하루 실행 상한(5.2절): 로그인·실행 키 검사는 **없다**(D8). 대신 사무실(`ws`)별로 이번 요청에서 accepted가 될 dispatch 수를 더했을 때 오늘(KST) 누계가 **50회**를 넘으면 429 `{ error: "daily_limit" }` → 토스트 "오늘 실행 한도를 넘었어요". 카운터는 인스턴스 메모리(날짜가 바뀌면 초기화)라 인스턴스마다 따로 세어 실제 상한은 느슨하다(R5). 예약 실행은 Worker를 거치지 않으므로 세지 않는다.
4. `WORKSPACES[ws].automations`에서 `automation`(또는 all이면 workflow 있는 전부)을 찾는다. 없거나 `workflow`가 없으면 404. **워크플로 파일명·ref·inputs는 항상 설정값**을 쓴다(클라이언트 값은 id뿐).
5. 자동화마다 `decideRun(latestRun, lastDispatchAt, now)`:
   - 최신 run이 `queued`/`in_progress` → `skipped: "already_running"`
   - 이 Worker 인스턴스가 60초 안에 같은 자동화를 dispatch 했음 → `skipped: "too_soon"`
   - 아니면 dispatch: `POST /repos/Junjaee/ai-office/actions/workflows/<file>/dispatches` body `{ "ref": "main", "inputs": { ...def.inputs, "request_id": requestId } }` → GitHub이 204면 `accepted`.
6. 응답(HTTP **200**) `{ results: [ { id, accepted: true, requestedAt } | { id, skipped: "already_running" | "too_soon" } ] }`. skipped는 오류가 아니므로 409 같은 별도 코드를 쓰지 않는다. GitHub이 401/403이면 `{ error: "github_auth" }` **502** → 화면 배너 "실행 연결이 끊겼어요". GitHub이 그 외 5xx/타임아웃이면 `{ error: "github_unavailable" }` 502 → 토스트 "GitHub 응답이 없어요".

응답 코드 요약: 200(results) / 400(본문·타입) / 405(메서드) / 403(출처) / 404(자동화 없음·workflow 없음) / 429(하루 상한 초과) / 502(GitHub 실패). 401은 없다(보호 없음, D8). 204는 **GitHub dispatch API의 응답**이지 `/api/run`의 응답이 아니다.

브라우저 쪽 응답 처리
- `accepted`인 자동화만 sessionStorage에 `{ requestId, at }`를 저장한다("all"이면 accepted된 각 id 아래 같은 requestId를 저장).
- `skipped`인 자동화는 **아무것도 저장하지 않는다**(저장하면 규칙 2가 최대 3분간 "시작 요청됨"을 잘못 표시). 토스트만 띄운다.
- 502·429·403은 저장 없이 토스트/배너.

GitHub 호출 공통 헤더: `Authorization: Bearer <GITHUB_TOKEN>`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, `User-Agent: ai-office-worker` (없으면 403).

"전체 시작"은 5번을 설정 순서대로 반복한다. 별도 디스패처 워크플로(run-all.yml)는 만들지 않는다. 실행기 1대(사무실 PC든 서버든)는 job을 하나씩 돌리므로 GitHub 큐가 순서를 맡는다.

### 4.3 `GET /api/status?ws=assembly`

Worker가 아래를 합쳐 돌려준다. 같은 `ws` 응답은 **모듈 스코프 메모리**(`let cache = { at, body }`)에 15초 캐시한다. Cache API는 쓰지 않는다(커스텀 도메인 뒤에서 동작 보장이 없음). 캐시가 인스턴스마다 따로 있어도 GitHub 5,000회/시 한도 안에 든다(4.8절).

```json
{
  "checkedAt": "2026-09-11T00:02:10Z",
  "config": { "canRun": true, "tokenExpiresAt": "2027-09-01T00:00:00Z" },
  "runs": {
    "minutes": { "id": 17234567890, "status": "in_progress", "conclusion": null,
                 "requestId": "req-20260911090001-a1b2", "startedAt": "…", "completedAt": null, "url": "…" }
  },
  "files": { "minutes": { …상태 파일 v2… } },
  "source": "github"
}
```

- `runs`: `GET /repos/{o}/{r}/actions/runs?per_page=30` 한 번으로 받아 `path`(워크플로 파일)로 자동화에 매핑, `conclusion`이 `cancelled`/`skipped`인 run은 건너뛰고 자동화마다 최신 1건. `requestId`는 `display_title`(= run-name)에서 파싱.
- `files`: `GET /repos/{o}/{r}/contents/public/status/{ws}/{id}.json?ref=main` (`Accept: application/vnd.github.raw+json`)로 직접 읽음 → push 뒤 수 초 안에 최신. 실패(토큰 만료 등)하면 `env.ASSETS.fetch("/status/{ws}/{id}.json")`(배포된 정적 파일)로 대체하고 `source: "static"`.
- `config.canRun`: `GITHUB_TOKEN` 설정 여부(값은 절대 내보내지 않음). `tokenExpiresAt`: GitHub 응답 헤더 `github-authentication-token-expiration`.
- 실행기 온라인 여부(runners API, PAT에 Administration:read 필요)는 **1차에서 쓰지 않는다**. "queued 90초 초과 → 실행기 기다리는 중"과 "36시간 초과 → 예약 실행이 밀리고 있어요"로 대신한다. 2차 옵션.

### 4.4 브라우저 쪽 (`app/status.ts` → `useLiveStatus(ws)`)

세 입력을 합쳐 3절 규칙에 넣는다.

| 입력 | 갱신 주기 | 역할 |
|---|---|---|
| 로컬 "요청됨" (sessionStorage `{ automationId: { requestId, at } }`) | `/api/run` 응답의 **`accepted` 항목에만** 저장(클릭 즉시가 아니라 응답 시점; 그 사이는 버튼 "요청 중…"). `skipped`·오류 응답은 저장하지 않음. 같은 requestId의 run이 보이거나 3분이 지나면 삭제 | 응답 직후 0초 반응 (같은 탭에서만) |
| `/api/status` | 평소 60초, 활성(요청됨·queued·running·finishing이 하나라도 있으면) 10초 | 일하는 중·끝남 판정의 주 입력 |
| 정적 `/status/<ws>/index.json` → `<id>.json` (기존 코드) | `/api/status`가 실패했을 때만 60초 | 폴백. `source = "static"`으로 규칙에 넣음 |

⚪ 배너 "최신 상태를 못 가져왔어요"는 **최종 `source`가 `"static"`이면** 띄운다 — `/api/status` 실패로 브라우저가 폴백했든, Worker가 `source:"static"`으로 응답했든 같다. `runs`가 없는 경우(브라우저 폴백)에는 규칙 2~6이 걸리지 않고 파일 기반 규칙 7~11만 작동한다.

파생 결과 `AutomationView[]` → (1) 요약 4칸 (2) 엔진 `apply()` (3) 카드 (4) 배너(`warn` 집계).

### 4.5 토큰·설정 보관

| 값 | 어디에 | 방법 |
|---|---|---|
| `GITHUB_TOKEN` (fine-grained PAT) | Cloudflare 워커 **`ai-office`** Secret | 대시보드 Workers & Pages → ai-office → Settings → Variables and Secrets → Add (type Secret). 비개발자에게 CLI보다 쉽고, 로컬 `wrangler secret put`은 `dist/server/wrangler.json`의 이름(`assembly-office`) 때문에 **다른 워커를 만들 수 있으니 쓰지 않는다** |

### 4.6 워크플로 변경 (`.github/workflows/minutes.yml`)

```yaml
on:
  schedule: [{ cron: "0 0 * * *" }]
  workflow_dispatch:
    inputs:
      request_id:
        description: "화면에서 누른 요청 id (비워도 됨)"
        type: string
        default: ""
run-name: ${{ github.event_name == 'workflow_dispatch' && format('수집 · {0}', inputs.request_id) || '수집 · 예약' }}
```

- `mode: dry-run` 입력 **삭제**(상태 파일을 쓰지 않아 화면과 어긋남. 개발자는 로컬에서 `--dry-run`).
- `run-name`에 request_id를 넣어 runs API `display_title`로 "내가 누른 실행"을 결정적으로 매칭.
- **`GOOGLE_REFRESH_TOKEN` 검사 step은 워크플로에서 삭제한다**(지금은 없으면 `exit 0`). 워크플로에서 `exit 1` 하면 Python이 돌지 않아 `ok:false` 파일도 한국어 문구도 남지 않는다. 대신 **Python이 검사**한다: 토큰이 비어 있으면 `errors.py`의 "구글 드라이브 인증이 없거나 만료됐어요"로 `report(ok=False)` 후 `return 1`(4.7절). 이렇게 해야 잡 실패 + 파일 + 화면 문구가 모두 생긴다.
- 수집 step에 `env: REQUEST_ID: ${{ inputs.request_id }}` 추가.
- concurrency `group: minutes / cancel-in-progress: false` 유지(실행 1 + 대기 1, 새 대기가 이전 대기를 교체).
- **`runs-on: [self-hosted, kr-office]`가 실행기 선택(D0)에 따라 바뀌는 유일한 지점.** 사무실 PC든 국내 IP 서버(예: Oracle Cloud 무료 티어 서울·춘천 리전)든 같은 라벨로 self-hosted runner를 등록하면 워크플로·Worker·화면은 그대로다. GitHub 호스트 러너(`ubuntu-latest`)는 해외 IP라 국회 수집엔 쓰지 않는다(`diag.yml`의 진단 잡만 예외).

### 4.7 자동화(Python) 변경

`automations/common/report_status.py`
- `report(...)`에 `tasks: list[dict] | None`, `started_at: str = ""`, `duration_sec: int | None` 인자 추가. `run_id`/`run_url`/`request_id`/`trigger`는 환경변수(`GITHUB_RUN_ID`, `GITHUB_SERVER_URL`, `GITHUB_REPOSITORY`, `REQUEST_ID`, `GITHUB_EVENT_NAME`)에서 자동으로 채움.
- push 실패 시 `pull --rebase` 후 **3회 재시도**(자동화가 여러 개가 되면 동시 push 경합).
- 시작 시 `running=true` 커밋은 **하지 않는다**(재배포 1회 추가·수집 2분이라 끝난 뒤에야 보임. runs API가 대신). 따라서 규칙 7은 새 파일에는 걸리지 않는다.

`automations/minutes/collect_minutes.py`
- `run()` 본문을 `try/except`로 감싼다. 사실 정정: 지금도 예외는 전파되어 잡(job)은 실패하지만 **상태 파일이 남지 않아** 화면이 원인을 모른다. 예외 시 `report(..., ok=False, summary=<한국어 한 줄>, log_lines=[원문 앞 300자])`가 **push까지 끝난 뒤** `return 1`. (push가 3회 모두 실패하면 파일 없이 잡만 실패 → 규칙 5의 "실행 실패 · 자세한 기록 보기"로 보인다.)
- 시작 직후 `GOOGLE_REFRESH_TOKEN`(과 필수 환경변수)이 비어 있으면 위 경로로 "구글 드라이브 인증이 없거나 만료됐어요"를 남기고 `return 1`(4.6절의 워크플로 검사 대체).
- 알려진 예외 → 한국어 매핑(`automations/common/errors.py`, 테스트 포함):

| 예외 / 상황 | summary |
|---|---|
| `requests.ConnectionError`/`Timeout` (assembly.go.kr) | "국회 사이트에 연결할 수 없어요" |
| `GOOGLE_REFRESH_TOKEN` 없음 · `google.auth.exceptions.RefreshError` | "구글 드라이브 인증이 없거나 만료됐어요" |
| 디스크 부족(`min_free_gb`) | "저장 공간이 부족해요" |
| 그 외 | "실행 중 문제가 생겼어요" |

- `tasks` 조립: `collect` → `counts.error == 0 ? done : error`, summary "신규 N건"; `replace` → 항상 `done`, summary "교체 N건". `audit`(국감·국조)는 설정에 `planned: true`라 파일에 넣지 않는다.
- 하위 작업 id는 `config.actions.yaml`의 `tasks:` 절에서 읽는다(Python이 TS 설정을 읽을 수 없으므로). **원천은 `app/workspaces/assembly.ts`이고 yaml은 복제본**이다. 둘의 일치는 `tests/workspaces.test.mjs`가 강제한다(7.4절): 워크플로가 있는 자동화마다 yaml `tasks:`의 id 집합 == 사무실 설정의 planned 아닌 `tasks[].id` 집합.

## 5. 보안 (실행 버튼 보호)

### 5.1 위협과 사용자 결정

사이트는 공개 URL, 저장소는 비공개, 실행은 **자체 실행기(사무실 PC 또는 국내 서버)**에서 일어난다. `/api/run`이 무방비면 주소를 아는 누구나 (a) 실행기에서 수집을 반복시키고 (b) 국회 사이트·드라이브 요청을 소모시키며 (c) 상태 커밋·재배포를 유발한다. 피해 상한은 GitHub concurrency(실행 1 + 대기 1)와 Worker의 중복 실행 방지·하루 상한으로 제한된다.

**사용자 결정(11절 질문 2, D8): 실행 버튼에 Cloudflare Access(로그인)도 실행 키(PIN)도 도입하지 않는다.** 사이트를 볼 수 있으면 누구나 [시작]을 누를 수 있다. 이 결정의 위험(주소가 새면 누구나 실행 가능, 하루 상한까지 낭비 가능)은 10절 R15에 기록한다. 현재 인증 없는 `/api/report`(Notion·Discord 발행)는 스팸 경로라 삭제한다.

### 5.2 남는 보호

- **사이트 주소 비공개 유지**: workers.dev 주소(또는 커스텀 도메인)를 공개 문서·SNS·검색에 노출하지 않는다. 사실상 유일한 접근 통제이므로 README·CLAUDE.md에 수칙으로 적는다.
- **중복 실행 방지(Worker)**: dispatch 전 runs API로 queued/in_progress 확인 → `skipped: "already_running"`. 이것이 **유일한 권위**이고 60초 간격(`too_soon`)은 보조. GitHub concurrency(실행 1 + 대기 1, 새 대기가 이전 대기를 교체)는 3중 방어. 따라서 "연타로 대기열이 쌓인다"는 일은 없다.
- **하루 실행 요청 상한(Worker)**: 사무실(`ws`)당 하루 **50회**(accepted된 dispatch만 셈, KST 자정 초기화, 상수 `DAILY_RUN_LIMIT`). 초과 시 429 `{ error: "daily_limit" }` → 토스트 "오늘 실행 한도를 넘었어요". 카운터는 인스턴스 메모리라 인스턴스마다 따로 세어 실제 상한은 느슨하다(필요하면 KV로 이전, R5). 예약 실행은 Worker를 거치지 않으므로 세지 않는다.
- **GitHub 토큰 최소 권한**: `GITHUB_TOKEN`은 Worker Secret에만 두고, 권한은 **해당 저장소 하나**의 **Actions: Read and write + Contents: Read**로 최소화한다(5.3절). 주소가 새더라도 할 수 있는 일은 "이 저장소의 워크플로를 하루 상한까지 돌리기"뿐이며 코드·시크릿·다른 저장소에는 닿지 않는다.
- **출처 확인(유지)**: `Origin`이 있는데 호스트가 다르면 403(1차), `Sec-Fetch-Site: cross-site`면 403(보조). 헤더가 아예 없는 요청(curl)은 통과.
- **서버 측 허용 목록**: 워크플로 파일명·ref·inputs는 사무실 설정에서만, 클라이언트 입력은 id뿐.
- CORS 헤더를 내보내지 않는다. 응답에 토큰 값을 싣지 않는다(설정 여부 boolean만).
- 나중에 보호가 필요해지면: Cloudflare Access(사이트 전체 이메일 로그인, 무료 50명)를 대시보드에서 켜는 것이 가장 단순하며, 이 문서의 코드는 그때도 바꾸지 않아도 된다.

### 5.3 GitHub 토큰(PAT)

- fine-grained PAT, Resource owner Junjaee, 저장소 **ai-office 하나만**, 권한: **Actions: Read and write**(dispatch·runs), **Contents: Read**(상태 파일 직접 읽기), Metadata: Read(자동). Administration:read는 1차에서 불필요.
- 만료: **"만료 없음"을 선택할 수 있으면 그것, 아니면 허용 최대(1년)**. 90일은 운영 부담만 키운다.
- Worker가 GitHub 응답 헤더 `github-authentication-token-expiration`을 읽어 `tokenExpiresAt`으로 내보내고, 화면은 30일 전부터 "실행 연결이 N일 뒤 끊겨요" 배너를 띄운다. 만료 뒤에는 dispatch가 401 → "실행 연결이 끊겼어요 · 설정을 다시 해야 해요"(다른 기능은 정상).
- 토큰은 Cloudflare Secret에만. 코드·`.dev.vars.example`·커밋·응답·로그 어디에도 값 금지.
- 상태 파일 push는 러너의 `GITHUB_TOKEN`(contents: write, 잡 종료 시 만료)이 하므로 PAT에 쓰기 권한은 필요 없다.

### 6.2 새 엔진의 공개 API (`app/game/engine.ts`)

```ts
export type Agent = {
  id: string; name: string; role: string; deptId: string; automationId: string;
  hair: string; shirt: string; accent: string; skin: string;
  x: number; y: number; facing: Facing; anim: Anim; state: TaskState;
};
export class OfficeEngine {
  constructor(seeds: StaffSeed[], rooms: Room[], lounge: Room);   // 숨긴 부서 seed는 넘기지 않음
  readonly agents: Agent[];
  place(input: OfficeInput): void;                  // 첫 로드: 걷기 없이 상태에 맞는 위치(라운지 좌석/책상)에 즉시 배치
  apply(input: OfficeInput): boolean;               // 바뀐 직원만 갱신, 바뀐 게 있으면 true
  tick(dt: number): boolean;                        // 걷는 중인 직원만 경로를 따라 위치 갱신. 아무도 안 걸으면 false
  hotRoom(): string | null;                         // 첫 running 부서
}
```

`apply`는 `office-model.ts`의 `poseFor(state)`·`placeFor(state)`·`needsWalk(prev, next)`를 쓴다. 상태가 바뀌었을 때: (1) `needsWalk`가 false면 제자리에서 `anim/facing/state`만 바꾸고, (2) true(쉬는 중↔책상)면 **목적지(라운지 좌석 또는 자기 책상)를 계산 → `pathfinding`으로 경로를 얻어 걷기 시작 → 도착 시 `poseFor(state)` 자세로 전환**한다. 걷는 도중 상태가 또 바뀌면 현재 위치에서 새 목적지로 경로를 다시 계산한다. 각본·랜덤 타이머·큐는 없고, `tick`은 걷는 직원이 있을 때만 의미가 있다(OfficeWorld가 그동안만 rAF를 돌림). 라운지 좌석은 `lounge`의 좌석 좌표를 순서대로 배정하고 모자라면 라운지 안 빈 타일에 서서 대기(a-idle). OfficeWorld는 `apply`/`tick`이 true를 돌려줄 때만 재렌더한다.

## 9. 단계별 구현 계획

각 단계는 이전 단계의 완료 기준을 통과한 뒤 시작한다. 1·2단계는 현재 화면과 호환되므로 먼저 배포해 실측할 수 있다. **화면에 실제 버튼을 얹는 것은 4단계에서 엔진·화면을 한꺼번에 바꿀 때만** 한다(가짜 각본과 실제 버튼이 한 화면에 공존하는 중간 산출물을 내지 않는다).

### 0단계 — 검증 게이트 (사용자 + 개발자, 0.5~1일)

할 일
0. **11절 질문 1(실행기 위치)은 "미정, 구현은 둘 다 지원"으로 기록됐다.** 0단계에서 실행기를 어디에 둘지 확정할 필요는 없다. 게이트는 **"어떤 실행기든 1대 등록해 첫 실행 성공"**이다. 사무실 PC면 `automations/runner/setup-office-runner.ps1`, 국내 IP 서버(예: Oracle Cloud 무료 티어 서울·춘천 리전 VM)면 GitHub의 리눅스 self-hosted runner 설치 절차로, 어느 쪽이든 같은 라벨(`self-hosted`, `kr-office`)을 붙여 등록한다. 워크플로는 바꾸지 않는다(4.6절 `runs-on`).
1. 실행기 등록(현재 **0대**). GitHub Settings → Actions → Runners에 등록한 실행기가 Idle로 보이는지 확인. 사무실 PC면 절전 해제·재부팅 후 서비스 자동 시작, 서버면 systemd 자동 시작 확인.
2. Actions → "진단 (네트워크)" 실행 → self-hosted 잡에서 국회 사이트·구글·GitHub 200 확인(국내 IP 확인).
3. Actions → "국회회의록 수집" 수동 실행(daily). 완료 후 (a) main에 `ai-office-bot`의 `status: minutes …` 커밋이 올라오는지 (b) Cloudflare Workers Builds가 그 push로 재배포되는지 (c) 사이트의 `/status/assembly/minutes.json` `updated_at`이 바뀌는지, (d) 드라이브 업로드 포함 실제 소요 시간, (e) **push → 재배포 완료까지 실제 시간**(문서의 "3~10분"을 이 값으로 확정) 확인.
4. Cloudflare 대시보드에서 실제 워커 이름(`ai-office`)과 Workers Builds 배포 이름·빌드 시간·무료 한도 확인. 커스텀 도메인 사용 여부 확인.
5. fine-grained PAT 발급(Actions RW + Contents R, 만료 최대) → 워커 `ai-office` Secret `GITHUB_TOKEN` 등록.
6. (질문 2 답변 "보호 없음" 기록됨) Access·`RUN_KEY` 설정은 없다. 사이트 주소를 공개하지 않는다는 수칙만 확인.

완료 기준
- 실행기(종류 무관) 1대 Idle, 워크플로 실행 이력 ≥ 1건 성공, 봇 커밋 ≥ 1건, 재배포 확인(안 되면 10절 R2 대응 확정), 실측 소요 시간(수집·재배포) 기록.
- 이 게이트를 통과하기 전에는 Worker·화면·엔진 코드를 시작하지 않는다.

| 탭 A에서 [시작] 직후 탭 B(또는 다른 사람)에서 [시작] | B는 토스트 "이미 실행 중이에요", B의 카드는 다음 폴링(≤10초) 때 일하는 중으로. B의 sessionStorage에는 아무것도 저장되지 않음 |
| [전체 시작] (하나는 이미 실행 중) | 토스트 "N개 시작 요청, 1개는 이미 실행 중", accepted된 것만 즉시 "시작 요청됨" |
| 실행기 끄고 [시작] | 90초 뒤 "실행기 기다리는 중" + 노란 배너, 실행기 켜면 이어짐 |
| 실행기를 36시간 이상 끈 채 예약 시각 경과(모의: 상태 파일 `updated_at`을 2일 전으로) | 카드 "쉬는 중 · 예약 실행이 안 되고 있어요 · 마지막 실행 N시간 전" + 노란 배너 "예약 실행이 밀리고 있어요…". 실행기 켜고 [시작] 성공 후 배너 사라짐 |
| 하루 상한 초과(모의: `DAILY_RUN_LIMIT`을 2로 낮춰 3번째 요청) | 429 → 토스트 "오늘 실행 한도를 넘었어요", sessionStorage 저장 없음, 카드 상태 변화 없음 |
| `GOOGLE_REFRESH_TOKEN` 비움 | 잡 실패 + 파일 남음 → 카드 **오류 · "구글 드라이브 인증이 없거나 만료됐어요"** (규칙 5, 같은 run 파일 우선) + 자세한 기록 링크 |
| PAT 권한에서 Contents 제거 | `source: "static"`으로 폴백, ⚪ 배너 "최신 상태를 못 가져왔어요", 끝남 반영 **3~10분**(0단계 실측값) |
| Worker 배포를 잠깐 깨뜨림(`/api/status` 5xx) | 브라우저가 정적 폴백, 같은 ⚪ 배너. 일하는 중 판정은 못 하고 파일 기준만 표시 |
| PAT 삭제 | "실행 연결이 끊겼어요", 나머지 화면 정상 |
| 예약 실행(09:00) 다음 날 관찰 | 끝남으로 갱신, `trigger: "schedule"` |

통과 후 사용자에게 화면 어휘 최종 확인.

### 총 공수

1인 기준 **7~8 작업일** (게이트 0.5~1 · 파이프라인 0.5~1 · Worker 1 · 설정 0.5 · 엔진·화면 2.5~3 · 문서 0.5 · 검증 1). 사용자 작업: 남은 질문 답변 + 실행기 설치(사무실 PC 10분 / 국내 서버 약 30분) + 첫 실행 확인 + PAT 발급·시크릿 입력 ≈ 1시간(안내문 보고). 이후 상시: 실행기 켜 두기(어디에 두든).

## 10. 위험과 대안

| # | 위험 | 대응 |
|---|---|---|
| R1 | **실행기 미등록/오프라인**(현재 0대). dispatch는 204로 성공하지만 run이 queued로 남고 24시간 뒤 자동 취소. 예약 실행도 밀림. 취소 뒤에는 run 자체가 사라져 화면이 조용해질 수 있음. 실행기를 어디에 둘지(사무실 PC/국내 서버)도 아직 미정 | 실행기 종류와 무관하게 상시 가동이 전제(D0). 위치 미정이 코드 변경을 부르지 않도록 `runs-on` 라벨 하나로 옮길 수 있게 구현(4.6절). 0단계 게이트("어떤 실행기든 1대 등록해 첫 실행 성공"). 화면 "실행기 기다리는 중" + 배너(규칙 3), 취소 뒤에는 "예약 실행이 밀리고 있어요" 배너(규칙 10a, D11). 실행기 README의 절전·서비스 자동 시작 수칙(사무실 PC) / systemd·무료 티어 회수 정책(서버). 2차: runners API(Administration:read)로 온라인 여부 직접 표시 |

| R3 | Workers Builds 무료 플랜 직렬 빌드로 정적 폴백이 **3~10분** 지연, 빌드 분 소모 | Contents API가 기본이라 체감 없음. 2차: watch paths에서 `public/status/**` 제외 |
| R4 | PAT 만료·권한 부족으로 버튼이 조용히 죽음 | 만료 최대/무기한, 30일 전 배너, 만료 시 배너, 다른 기능 정상. 갱신 절차 1쪽 문서 |

| R9 | Worker가 `app/workspaces`를 import할 때 브라우저 전용 코드가 섞임 | `index.ts`·`<id>.ts`는 순수 데이터(확인됨). `company.config.ts` import 금지 규칙을 CLAUDE.md에 명시 |

## 11. 사용자 확인이 필요한 질문

**질문 1. 실행기(자동화가 실제로 도는 컴퓨터)를 어디에 둘까요? — 사무실 PC / 국내 서버 / 미정(둘 다 지원되도록 구현)**
- 자동화는 GitHub Actions로 실행되지만, 국회 사이트가 해외 IP를 막아 GitHub이 제공하는 서버(해외 IP)로는 수집이 안 됩니다. 그래서 국내 IP를 가진 컴퓨터 한 대를 "실행기"로 등록해야 합니다. 어느 쪽이든 **실행기가 꺼져 있으면 "시작"을 눌러도 아무 일도 안 일어나고, 매일 09:00 예약 실행도 건너뜁니다.** 24시간 넘게 꺼져 있으면 눌러 둔 요청도 GitHub이 취소합니다. 화면은 실행기가 꺼진 것 같을 때 노란 배너로 알려줍니다.
- (가) 사무실 PC — 설치 10분. 절전 끄기(노트북은 덮개 닫아도 계속 켜짐 설정), 재부팅 후 실행기 서비스 자동 시작, 퇴근·주말에도 켜 두기가 필요.
- (나) 국내 IP 서버 — 예: Oracle Cloud 무료 티어 서울·춘천 리전 VM에 실행기 등록. PC를 켜 둘 필요가 없지만 서버 만들기·유지(무료 티어 유휴 회수 정책 확인)가 필요.
- (다) 미정 — 구현은 둘 다 지원. 워크플로의 `runs-on` 라벨 하나만 바꾸면 옮길 수 있게 만들고, 0단계에서는 어느 쪽이든 1대 등록해 첫 실행만 성공시킴.
- **답변(기록): (다) 미정, 구현은 둘 다 지원.** 실행기를 어디에 둘지는 별도 결정 사항으로 남깁니다.

**질문 2. 실행 버튼을 어떻게 보호할까요?**
- (가) 사이트 전체에 이메일 로그인(Cloudflare Access) — 처음 한 번 이메일로 인증 코드를 받고 로그인하면 한 달 동안 유지. 사이트 자체가 남에게 안 보임.
- (나) 실행 키(PIN) — 사이트는 누구나 보되, "시작" 버튼을 처음 누를 때 한 번 키를 입력.
- (다) 보호 없음 — 사이트를 볼 수 있으면 누구나 누를 수 있음. 사이트 주소를 공개하지 않는 것, Worker의 중복 실행 방지, 사무실당 하루 실행 상한(50회)으로만 막음(5절). 주소가 새면 누구나 실행할 수 있고 하루 상한까지 낭비될 수 있음(10절 R15).
- **답변(기록): (다) 보호 없음.** 나중에 필요해지면 (가)를 대시보드에서 켜는 것으로 코드 변경 없이 보강할 수 있습니다.

**질문 3. 사무실 그림을 "자동화가 있는 부서만" 그려도 될까요? (지금의 4열 3행 12방 고정 배치가 바뀝니다)**
- 지금은 부서 방 12개를 4열 3행으로 항상 그리고, 그중 9개는 자동화가 없어 회색입니다.
- (가) **추천: 자동화가 연결된 부서만 그림** — 국회 사무실은 지금 "회의록 수집" 방 하나만 보이고(1행), 자동화가 붙을 때마다 방이 늘어남(4열 유지, 행 수는 방 수에 맞춤). 요약 숫자에도 준비 중 부서는 안 들어감. 부서 12개의 내부 id는 그대로라 나중에 되돌리기 쉬움.
- (나) 지금처럼 12방 고정, 자동화 없는 부서는 회색 "준비 중"으로 표시 — 앞으로 할 일이 보이지만 화면이 회색 방 9개로 채워짐.
- 추천 답: **(가)**. 사무실 설정 한 줄(`showPlanned: true`)로 언제든 (나)처럼 준비 중 부서를 다시 보일 수 있습니다.
- **답변(기록): (가) 채택.**

**질문 4. 직원이 걸어 다니는 연출을 완전히 없앨까요?**
- (가) 완전히 없앰 — 직원은 항상 자기 책상에 있고 자세(앉기/타이핑/서기)와 배지만 바뀜. 관련 코드 약 300줄 삭제.
- (나) 페이지를 열 때 입구에서 자리로 걸어 들어오는 5초 연출만 남김(그 뒤로는 이동 없음).
- (다) **상태 변화에만 이동 — 채택** — 쉬는 중=라운지 소파에 앉음, 일하는 중=책상으로 걸어가 타이핑, 끝남=책상에서 ✓, 오류=책상 옆에 서서 !. 회의실·대표실(CEO 포함)은 삭제하고 라운지는 "쉬는 곳"으로만 남김. 랜덤 이동·잡담·커피·말풍선은 삭제. 페이지를 처음 열 때는 걷기 없이 각자 자리에 바로 놓이고, 그 뒤 상태가 바뀔 때만(쉬는 중↔책상) 걸어서 이동함.
- **답변(기록): (다) 채택.** 움직임이 곧 상태 변화의 표현이 되므로 "의미 없는 움직임" 불만은 해소되고, 라운지↔책상 이동으로 "지금 쉬는지 일하는지"가 한눈에 보입니다(D2, 2.3절).

**질문 5. 상태 이름 네 가지를 이대로 쓸까요? — 쉬는 중 · 일하는 중 · 끝남 · 오류**
- 대안: "오류" 대신 "문제 있음", "끝남" 대신 "완료".
- 추천 답: **이대로**. 문구는 파일 한 곳(`LABELS`)에 있어 나중에 바꿔도 코드 수정 없이 끝납니다.

**질문 6. "끝남"이 화면에 보이기까지 얼마나 기다려도 될까요?**
- (가) **추천: 약 30초** — 서버(Worker)가 GitHub에서 결과 파일을 직접 읽음. GitHub 토큰에 "저장소 내용 읽기" 권한을 하나 더 줌.
